# Inventory update workflow

This workflow is stored with the Site so a fresh background task can execute it. No credentials are included.

1. Read the linked Site using Sites and confirm it is owner-private: owner role, no viewers/editors/groups besides its owner, no external visitors. Stop if that is no longer true. Obtain the existing service access returned by Sites; never create or rotate a bypass token to inspect access. Keep it only in memory. Read the existing `/api/inventory` through the same service access.
2. Read `src/discover.mjs` from the Site's exact published source commit or authorised source checkout. Execute the self-contained `discoverSites` function through the connected Cloudflare execution capability, passing its `cloudflare.request` function. Remove only the ES module `export` keyword for that environment. Use the same Cloudflare account selection as the task's connection. The function lists all currently accessible accounts and fails on an incomplete read. It contains only GET requests. Do not read secrets or change Cloudflare resources.
3. If the complete resource inventory has not changed, finish quietly. If an hourly task is active, set `syncCadence` to `hourly`. For a health check after an unchanged collection, write the new sync timestamp so the gallery can distinguish a working task from stale data. Never claim hourly sync is active before a saved enabled hourly task exists.
4. POST the entire collected result as JSON to the linked Site's `/api/inventory`. Use the exact origin returned by Sites and `OAI-Sites-Authorization: Bearer <existing service access>` only for that origin. Never log, persist or include that header in source. Updates must be serialised; do not overwrite after a stale-timestamp rejection.
5. Require HTTP success and `status: success`. GET `/api/inventory` again and compare the timestamp, count and IDs. A failed or partial collection must leave the last valid inventory intact. Do not republish code just to change inventory.
6. Report only sync failures requiring user action; routine healthy inventory updates should finish quietly.

The hourly background task is created through the published Site's supported scheduling controls after checking its linked automations. Its existence does not prove execution: the initial service write/readback verifies the writer separately. If provider access, service access or cloud scheduling is unavailable, report that blocker and leave the previous inventory in place. This workflow uses native connected tools in the cloud task; browser-only sessions and local previews are insufficient.
